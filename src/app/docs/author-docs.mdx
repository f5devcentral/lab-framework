## APICheck

The **APICheck** allows the lab author to check an API endpoint with an optional path and HTTP response code.
The component will also look up the target Docker component's ephemeral networking information if it's the target of the API check.

**Note**: you must supply either a **componentName** or a **url**.

| Variable             | Description                                                                                              | Required |
|----------------------|----------------------------------------------------------------------------------------------------------|----------|
| **componentName**    | The name of the component to check.                                                                      | Yes      |
| **path**             | The path to append to the component for the API check.                                                   | No       |
| **targetStatusCode** | The expected HTTP status code from the API check.                                                        | No       |
| **url**              | The URL to check.                                                                                        | Yes      |
| **tlsComponent**     | If a component name is specified, use TLS (https) to connect to the component. Default is no TLS (http). | No       |

### Examples

Calling APICheck with a component name:

```jsx
<APICheck 
componentName="nginx-plus-2" 
targetStatusCode={200} 
/>
```

<APICheck 
  componentName="nginx-plus-2" 
  targetStatusCode={200}  
/>

Calling APICheck with a component name and a path:

```jsx
<APICheck 
componentName="nginx-plus-2" 
path="/example-path" 
targetStatusCode={200}  
/>
```

<APICheck 
  componentName="nginx-plus-2" 
  path="/example-path" 
  targetStatusCode={200}  
/>

Calling APICheck with a component name via TLS:

```jsx
<APICheck 
componentName="nginx-plus-2" 
targetStatusCode={200} 
tlsComponent={true}
/>
```

<APICheck 
  componentName="nginx-plus-2" 
  targetStatusCode={200} 
  tlsComponent={true}
/>

Calling APICheck with a url:

 ```jsx
<APICheck  
targetStatusCode={200} 
url="http://f5.com" 
/>
```

<APICheck  
  targetStatusCode={200} 
  url="http://f5.com" 
/>

## Container for API Checks

The framework uses the **APICheckContainer** wrapper component to help correctly display all individual **ApiCheck**, **APIHeaderCheck**, and **APIResponseCheck** components in the lab guide. This is useful if you need to group together more than one of the preceding components.

### Examples

Grouping more than one check component:

```jsx
<APICheckContainer>
  <APICheck 
  componentName="nginx-plus-2" 
  targetStatusCode={200}  
  />
  <APIHeaderCheck
    headerName="Server"
    headerValue="nginx/1.25.5"  
    targetStatusCode={200} 
    url="https://api.example.com" 
  />
  <APIResponseCheck 
    componentName="nginx-plus-2" 
    path="/example-path" 
    searchString="nginx"
    targetStatusCode={200}  
  />
</APICheckContainer>
  ```

## Docker Component

The lab framework allows you to deploy docker containers within the lab guide.

The framework uses the **DockerContainer** wrapper component to help correctly display all individual **Docker** components in the lab guide.

The **Docker** component is responsible for managing and displaying information about the container.  

| Variable        | Description                                                                 | Required |
|-----------------|-----------------------------------------------------------------------------|----------|
| **name**        | A unique name for the Docker container.                                     | Yes      |
| **description** | The description of the Docker container.                                    | No       |
| **image**       | The image of the Docker container.                                          | Yes      |
| **env**         | The environment variables for the Docker container.                         | No       |
| **port**        | The port mapping for the Docker container.                                  | No       |
| **attrs**       | Additional attributes for the Docker container.                             | No       |

Each environment entry supports the optional `resolveTemplates` flag. When set to `true`, template placeholders like `${PETNAME}` are resolved before the container is created. This behavior is intentionally opt-in and defaults to off.

### Examples

```jsx
<DockerContainer>
  <Docker 
    name="nginx-plus-1" 
    description="This is an example Docker container." 
    image="private-registry.nginx.com/nginx-plus/agent:debian" 
    env={[
      { name: "NGINX_AGENT_SERVER_HOST", value: "value", isVariable: false },
      { name: "NGINX_AGENT_SERVER_TOKEN", isVariable: true, isSecret: true }
    ]} 
    port={{host: 55055, container: 80}}
    attrs={[
      { name: "volume", value: "<path to folder on Docker host>/ssl:/etc/nginx/ssl" }
    ]}
  />
  <Docker
    name="nginx-plus-2"
    image="private-registry.nginx.com/nginx-plus/agent:debian"
  />
 </DockerContainer>
```
<br />

<DockerContainer>
  <Docker 
    name="nginx-plus-1" 
    description="This is an example Docker container." 
    image="private-registry.nginx.com/nginx-plus/agent:debian" 
    env={[
      { name: "NGINX_AGENT_SERVER_HOST", value: "agent.connect.nginx.com" },
      { name: "NGINX_AGENT_SERVER_TOKEN", isVariable: true, isSecret: true },
      { name: "NGINX_AGENT_LABELS", value: "config-sync-group=${PETNAME}", resolveTemplates: true }
      ]} 
    port={{host: 55055, container: 80}} 
  />
  <Docker
    name="nginx-plus-2"
    image="private-registry.nginx.com/nginx-plus/agent:debian"
  />
</DockerContainer>

The `${VAR}` syntax is only expanded when you set `resolveTemplates: true` on the environment entry. For example, `config-sync-group=${PETNAME}` resolves to the current stored value for `PETNAME` before the container is created only when that flag is enabled.

## KubernetesShell

The **KubernetesShell** provides a restricted command line for the lab user and displays the output of each command.

Only the `oc` and `kubectl` CLIs can be run. Commands are executed on the server without a shell, so shell operators such as `;`, `|`, `&&`, backticks, and redirection are rejected. Quoted arguments are supported.

The shell retains commands after they are run. Press the Up and Down arrow keys in the command input to navigate the history; Down restores any unfinished command after the newest history entry. Its initial prompt disappears when the first command is submitted.

| Variable        | Description                                                        | Required |
|-----------------|--------------------------------------------------------------------|----------|
| **title**       | The heading shown above the shell. Defaults to `Kubernetes Shell`. | No       |
| **placeholder** | The input placeholder text. Defaults to `kubectl get pods`.        | No       |
| **context**     | Pins commands to a kubeconfig context via `--context`.             | No       |
| **namespace**   | Pins commands to a namespace via `--namespace`.                    | No       |

Without **context** or **namespace**, commands use the active context of the kubeconfig the server was started with. When set, the flags are inserted directly after the CLI name, so a `--` passthrough such as `kubectl exec pod -- ls` still works.

If the kubeconfig is missing or the cluster cannot be reached, the shell reports that the cluster is unavailable along with the underlying CLI error, instead of only showing a raw connection failure.

### Example

```jsx
<KubernetesShell />
```

<KubernetesShell />

With a custom title and placeholder:

```jsx
<KubernetesShell
  title="OpenShift Console"
  placeholder="oc get projects"
/>
```

<KubernetesShell
  title="OpenShift Console"
  placeholder="oc get projects"
/>

Pinned to a context and namespace:

```jsx
<KubernetesShell
  namespace="default"
  placeholder="kubectl get pods"
/>
```

<KubernetesShell
  namespace="default"
  placeholder="kubectl get pods"
/>
